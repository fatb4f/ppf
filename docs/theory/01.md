# 0. Core semantic model

```text
DOMAIN
  │ defines nouns, invariants, lifecycle, failure semantics
  ▼
VARIABILITY AXIS
  ├─ construction varies ───────► factory / builder / provider
  ├─ algorithm varies ──────────► strategy / HOF / policy function
  ├─ representation varies ─────► adapter / mapper / serializer
  ├─ control flow varies ───────► orchestrator / state machine / workflow
  ├─ effects vary ──────────────► port + adapter / dependency injection
  └─ lifecycle varies ──────────► context manager / supervisor / pool
  ▼
CONTRACTS
  ▼
IMPLEMENTATIONS
  ▼
COMPOSITION
  ▼
EXECUTION
  ▼
OBSERVATION + TESTS
```

## Layer contract

```text
Operation function
    = performs one semantic verb

Higher-order function
    = accepts/returns operation functions
    = adds reusable execution policy

Factory
    = selects or constructs an implementation

Orchestrator
    = controls when and in what order operations execute

Adapter
    = translates an abstract operation into a concrete external effect

Domain model
    = defines what states and transitions are valid
```

```text
    [construction varies] ─────► C
    [algorithm varies] ────────► A
```

```text
C: CONSTRUCTION

  one concrete type
    └─► direct constructor

  one product, multiple implementations
    └─► factory function

    └─► factory method

    └─► abstract factory / dependency bundle

    └─► builder

    └─► prototype / copy

    └─► registry + factory
```

```text
A: ALGORITHM / POLICY

  interchangeable algorithm
    └─► strategy function or Protocol

  reusable wrapper policy
    └─► HOF / decorator

  choose handler by type
    └─► singledispatch / pattern matching

  ordered handlers
    └─► chain of responsibility

  aggregate collection
    └─► map / filter / reduce / fold

  lazy sequence
    └─► generator / iterator
```

```text
F: CONTROL FLOW

  linear transformation
    └─► pipeline

  dependency-directed execution
    └─► DAG executor

  branching and explicit transitions
    └─► state machine

  long-running multi-step process
    └─► process manager / workflow

  desired-state convergence
    └─► reconciler

  distributed rollback requirements
    └─► saga

  worker lifecycle and restart
    └─► supervisor
```

```text
E: EFFECT BOUNDARY

  external service
    └─► port + adapter

  multiple backends
    └─► adapter factory

  command routing
    └─► command bus / dispatcher

  event distribution
    └─► observer / event bus

    └─► repository interface + adapters
```

```text
L: LIFECYCLE

  acquire / release
    └─► context manager

  shared expensive resource
    └─► pool / provider

  cached immutable objects
    └─► flyweight / cache

  async sibling tasks
    └─► task group

    └─► supervisor + retry policy
```

## 2.1 Parsing and serialization

```text
Input bytes/text
  ▼
detect format
  ▼
parser factory
  ▼
selected parser strategy
  ▼
parse operation
  ▼
normalized domain object
  ▼
validator
```

| Concern                  | Pattern                     | Why                                         |
| ------------------------ | --------------------------- | ------------------------------------------- |
| JSON/YAML/TOML selection | Factory                     | Format determines implementation            |
| Parsing algorithm        | Strategy                    | Same contract, different algorithm          |
| Recursive syntax         | Composite                   | Nodes contain child nodes                   |
| Traversal                | Visitor or `singledispatch` | Operations vary independently of node types |
| Streaming                | Iterator/generator          | Avoid loading the entire input              |
| Normalization            | Pipeline                    | Ordered transformations                     |

```python
Parser = Callable[[str], Document]

def make_parser(format_name: str) -> Parser:
    return {
        "json": parse_json,
        "yaml": parse_yaml,
    }[format_name]
```

# 3. Factory pattern decision DAG

```text
Need to create something?
  │
  ├─ no ─► use an operation function
  │
  └─ yes
      │
      ├─ constructor is stable and obvious
      │   └─► direct construction
      │
      ├─ input/config selects one implementation
      │   └─► factory function
      │
      ├─ class exposes alternate semantic constructors
      │   └─► classmethod factory
      │
      ├─ subclass decides concrete product
      │   └─► factory method
      │
      ├─ multiple products must be mutually compatible
      │   └─► abstract factory
      │
      ├─ object requires ordered construction steps
      │   └─► builder
      │
      ├─ object is copied from a configured template
      │   └─► prototype / copy
      │
      └─ implementation is discovered dynamically
          └─► registry + factory
```

## Python preference order

```text
1. direct constructor
2. factory function
3. classmethod alternate constructor
4. callable dependency/provider
5. registry + factory
6. abstract factory object
7. class-heavy GoF implementation
```

### Reason

```text
Python functions are first-class
  ▼
behavior does not require a class
  ▼
many Strategy / Command / Factory Method examples collapse into callables
  ▼
classes remain useful when state, lifecycle or multiple related methods exist
```

```text
Operation:
```

# 7. HOF contract

```text
HOF:
    input:
      operation function
      policy/configuration

    output:
      operation function with preserved semantic contract

    owns:
      reusable execution policy

    does not own:
      domain-specific workflow order
```

## Composition DAG

```text
base operation
  ▼
validation wrapper
  ▼
authorization wrapper
  ▼
retry wrapper
  ▼
timeout wrapper
  ▼
tracing wrapper
  ▼
callable operation
```

```python
Operation = Callable[[Input], Output]

def traced(op: Operation) -> Operation:
    def wrapped(value: Input) -> Output:
        record_start(op)
        try:
            return op(value)
        finally:
            record_end(op)

    return wrapped
```

## Common HOF domains

| Policy             | HOF shape                                   |
| ------------------ | ------------------------------------------- |
| Retry              | `Operation -> Operation`                    |
| Timeout            | `Operation -> Operation`                    |
| Logging            | `Operation -> Operation`                    |
| Authorization      | `Operation -> Operation`                    |
| Validation         | `Operation -> Operation`                    |
| Caching            | `Operation -> Operation`                    |
| Mapping            | `(A -> B) -> Iterable[A] -> Iterable[B]`    |
| Filtering          | `(A -> bool) -> Iterable[A] -> Iterable[A]` |
| Folding            | `(B, A -> B) -> B`                          |
| Dependency binding | `partial(function, dependency=x)`           |

| ----------------- | --------------------: | -------------------: | ------------: | ------------------: | -----------------: |

# 9. Runtime execution DAG

```text
R0: RECEIVE
  input:
    CLI / HTTP / event / scheduled trigger

  action:
    parse transport representation

  output:
    request DTO

  transition:
    [parse success] ─► R1
    [parse failure] ─► transport error
```

```text
R1: NORMALIZE

  action:
    canonicalize values
    apply defaults

  output:
    normalized request

  transition:
    [normalized] ─► R2
```

```text
R2: VALIDATE CONTRACT

  action:
    structural validation
    invariant validation

  transition:
    [valid] ─► R3
    [invalid] ─► rejection
```

```text
R3: RESOLVE IMPLEMENTATIONS

  action:
    factory selects adapters and strategies

  output:
    dependency bundle

  transition:
    [all capabilities available] ─► R4
    [missing capability] ─► configuration failure
```

```text
R4: COMPOSE POLICIES

  action:
    apply HOFs:
      retry
      timeout
      trace
      authorize

  output:
    executable operations

  transition:
    [composition valid] ─► R5
```

```text
R5: BUILD PLAN

  action:
    project request into steps/dependencies

  output:
    execution plan or DAG

  transition:
    [plan valid and acyclic] ─► R6
    [invalid plan] ─► planning failure
```

```text
R6: ORCHESTRATE

  action:
    schedule ready nodes
    invoke operations
    collect results
    update workflow state

  transitions:
    [step success] ─► next ready node
    [retryable failure] ─► retry policy
    [compensable failure] ─► compensation
    [repairable failure] ─► repair state
    [terminal failure] ─► failed
    [all nodes complete] ─► R7
```

```text
R7: JUDGE

  action:
    evaluate output against invariants

  transitions:
    [accepted] ─► R8
    [repair allowed] ─► R5
    [rejected] ─► terminal rejection
```

```text
R8: PUBLISH

  action:
    persist result
    emit evidence
    return response

  terminal state:
    completed
```

```text
    every transition covered by tests
```

# 13. Pattern-selection constraints

```text
Use a factory when:
  implementation identity varies
  construction requires policy
  caller should not know concrete type
```

```text
Do not use a factory when:
  constructor is stable
  only one implementation exists
  factory merely renames the constructor
```

```text
Use an HOF when:
  behavior wraps another behavior
  policy is reusable
  input/output contract remains stable
```

```text
Do not use an HOF when:
  wrapper controls an entire business workflow
  mutation and hidden state dominate
  execution order must be externally visible
```

```text
Use an orchestrator when:
  multiple operations form one use case
  order or branching matters
  failure changes subsequent behavior
  execution produces workflow state
```

```text
Do not use an orchestrator when:
  one operation is sufficient
  a simple pipeline expresses the flow
  the function only forwards arguments
```

```text
Use an adapter when:
  external representation differs
  technology should remain replaceable
  testing requires a fake implementation
```

# 15. Final compression

```text
Domain
  defines valid meaning

Factory
  chooses what implementation exists

Operation
  performs one verb

HOF
  modifies how one operation behaves

Orchestrator
  determines when operations run

Adapter
  determines how external effects occur

State machine
  determines which transition is legal

Reconciler
  repeats orchestration until observed state satisfies desired state
```

```text
Choose patterns from variability:

construction ─► factory
algorithm ────► strategy/HOF
representation ► adapter
sequence ─────► orchestrator
transition ───► state machine
convergence ──► reconciler
lifecycle ────► context manager/supervisor
```
