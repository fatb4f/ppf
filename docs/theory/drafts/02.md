# 1. Minimal ontology

A compact ontology that covers most application domains and design patterns:

```text
SYSTEM
├── DATA
│   ├── Value
│   ├── Entity
│   ├── Configuration
│   └── Result
│
├── RULE
│   ├── Type constraint
│   ├── Invariant
│   ├── Precondition
│   └── Postcondition
│
├── OPERATION
│   ├── Query        Data → Data
│   ├── Transform    Data → Data
│   ├── Decision     Data → Choice
│   ├── Command      Data → Effect
│   └── Constructor  Config → Capability
│
├── STATE
│   ├── Current state
│   ├── Event
│   └── Transition   State × Event → State
│
├── VARIATION
│   ├── Policy
│   ├── Strategy
│   ├── Implementation
│   └── Configuration
│
├── COMPOSITION
│   ├── Sequence
│   ├── Pipeline
│   ├── Branch
│   ├── Parallel group
│   └── Dependency graph
│
├── BOUNDARY
│   ├── Port
│   ├── Adapter
│   ├── Serializer
│   └── External resource
│
└── CONTROL
    ├── Factory
    ├── Dispatcher
    ├── Orchestrator
    ├── State machine
    ├── Supervisor
    └── Reconciler
```

## Minimal relation graph

```text
Data
  ──constrained-by──► Rule
  ──consumed-by─────► Operation
  ──produced-by─────► Operation

Operation
  ──selected-by─────► Policy
  ──constructed-by──► Factory
  ──wrapped-by──────► HOF
  ──ordered-by──────► Orchestrator
  ──implemented-by──► Adapter

State
  ──changed-by──────► Transition
  ──observed-by─────► Query
  ──driven-by───────► Event

Orchestrator
  ──executes────────► Operation
  ──evaluates───────► Result
  ──advances────────► State
```

# 2. Smaller seven-concept ontology

For practical Python development, this is usually sufficient:

```text
1. DATA
2. RULE
3. OPERATION
4. POLICY
5. BOUNDARY
6. COMPOSITION
7. STATE
```

Everything else is a specialization.

```text
Factory
  = Operation + Policy
  = choose/construct implementation

HOF
  = Operation over Operations
  = add reusable execution policy

Adapter
  = Boundary Operation
  = translate abstract capability into concrete effect

Orchestrator
  = Composition + State
  = control execution across multiple operations

State machine
  = State + Rules + Transition Operation

Reconciler
  = Observe + Decide + Act + Repeat
```

# 3. Common domain representation

A domain can be expressed as one tuple:

```text
Domain :=
(
  Data,
  Invariants,
  Operations,
  States,
  Transitions,
  Policies,
  Effects
)
```

Example:

```text
Document processing :=
(
  Data:
    RawDocument
    ParsedDocument
    ValidatedDocument

  Invariants:
    schema is recognized
    identifiers are unique

  Operations:
    parse
    normalize
    validate
    persist

  States:
    received
    parsed
    valid
    rejected
    persisted

  Transitions:
    received ─parse────► parsed
    parsed ─validate───► valid
    parsed ─failure────► rejected
    valid ─persist─────► persisted

  Policies:
    parser selection
    validation profile
    rejection severity

  Effects:
    read file
    write database
    publish event
)
```

Pattern selection follows directly from this tuple:

```text
multiple parsers
  ─► Strategy or factory

multiple storage systems
  ─► Port + adapter

ordered parse/validate/persist
  ─► Pipeline or orchestrator

explicit processing statuses
  ─► State machine

cross-cutting retries/tracing
  ─► HOF/decorator
```

# 4. Are dataclasses and algorithms equivalent to design patterns?

```text
No.
```

They are the **implementation substrate**, not the pattern itself.

```text
Dataclass
  = representation of data/state

Algorithm/function
  = transformation or decision

Design pattern
  = recurring arrangement of:
      data
      operations
      ownership
      variability
      control flow
      effects
```

## Correct relationship

```text
Dataclasses + functions
  ▼
provide primitive implementation elements
  ▼
combined according to recurring constraints
  ▼
produce a design pattern
```

Example:

```python
from dataclasses import dataclass
from typing import Callable


@dataclass(frozen=True)
class Document:
    content: str


Parser = Callable[[str], Document]
```

This alone is not a pattern.

Add implementation selection:

```python
def make_parser(format_name: str) -> Parser:
    parsers = {
        "json": parse_json,
        "yaml": parse_yaml,
    }
    return parsers[format_name]
```

Now the arrangement represents:

```text
Factory:
  discriminator:
    format_name

  products:
    parser functions

  result:
    selected parsing capability
```

# 5. Factory patterns at their lower-level form

A factory is not fundamentally OOP.

Its minimal semantic form is:

```text
Factory :=
    discriminator/configuration
      → implementation/capability
```

Or:

```python
Factory = Callable[[Config], Capability]
```

## Factory as an algorithm

```text
Input:
  configuration or discriminator

Algorithm:
  validate discriminator
  select implementation
  bind dependencies
  construct result

Output:
  object, function or capability bundle
```

A factory can return:

```text
object
function
closure
adapter
resource
dependency bundle
execution plan
```

It does not require classes.

# 6. Factory pattern projections

## Simple factory

```text
Config
  ▼
selection algorithm
  ▼
implementation
```

```python
def make_store(kind: str) -> Store:
    match kind:
        case "memory":
            return MemoryStore()
        case "sqlite":
            return SQLiteStore()
        case _:
            raise ValueError(kind)
```

---

## Functional factory

```text
Config
  ▼
select function
  ▼
Operation
```

```python
Parser = Callable[[str], Document]

def make_parser(kind: str) -> Parser:
    return {
        "json": parse_json,
        "yaml": parse_yaml,
    }[kind]
```

---

## Abstract factory

OOP presentation:

```text
Factory object
  ├─ create_reader()
  ├─ create_writer()
  └─ create_validator()
```

Functional/data-oriented presentation:

```python
@dataclass(frozen=True)
class DocumentCapabilities:
    read: Callable[[Path], Document]
    write: Callable[[Path, Document], None]
    validate: Callable[[Document], list[str]]
```

```text
Abstract Factory
  ≈ record/dataclass containing a compatible family of capabilities
```

---

## Builder

OOP presentation:

```text
builder.set_a()
builder.set_b()
builder.build()
```

Data-oriented equivalent:

```text
Configuration
  ▼
successive validated transforms
  ▼
complete value
```

```python
config = (
    default_config()
    | database_settings
    | logging_settings
)

application = build_application(config)
```

The distinguishing feature is not the builder class.

It is:

```text
partial state
  ──validated steps──► complete constructible state
```

---

## Factory Method

OOP presentation:

```text
base class calls overridable creation method
```

Underlying semantics:

```text
fixed algorithm
  +
injected constructor
```

Functional equivalent:

```python
def process(
    source: Source,
    make_parser: Callable[[], Parser],
) -> Result:
    parser = make_parser()
    return parser(source.read())
```

This is dependency injection using a constructor function.

# 7. Refactoring Guru patterns projected into Python primitives

| Pattern                 | Minimal semantics                 | Python projection                        |
| ----------------------- | --------------------------------- | ---------------------------------------- |
| Factory Method          | Inject construction decision      | Constructor callable                     |
| Abstract Factory        | Compatible family of constructors | Dataclass of callables                   |
| Builder                 | Staged construction               | Validated transforms/config accumulation |
| Prototype               | Derive value from existing value  | `copy`, `replace`                        |
| Strategy                | Select algorithm                  | Function value                           |
| Command                 | Reify requested operation         | Dataclass payload + handler              |
| Template Method         | Fixed flow, variable steps        | HOF with injected functions              |
| State                   | Behavior depends on current state | Tagged dataclass + transition function   |
| Visitor                 | Add operations over variants      | `match` or `singledispatch`              |
| Iterator                | Incremental traversal             | Generator                                |
| Observer                | Notify subscribers                | Callback collection/event stream         |
| Chain of Responsibility | Ordered conditional handlers      | Sequence of functions                    |
| Decorator               | Wrap operation                    | HOF/decorator                            |
| Adapter                 | Translate contracts               | Wrapper function/object                  |
| Facade                  | Simplified capability surface     | Module or service function               |
| Composite               | Uniform recursive structure       | Recursive dataclass                      |
| Mediator                | Central coordination              | Orchestration function/event router      |

# 8. Data-oriented equivalent of classic patterns

The closest data-oriented replacement for class-heavy GoF patterns is:

```text
Algebraic data types
  +
pure functions
  +
function values
  +
explicit state transitions
  +
effect adapters
  +
composition functions
```

In Python:

```text
dataclass / NamedTuple / TypedDict
  = product data types

Enum / Literal / union
  = sum data types

function
  = operation

Callable
  = strategy/capability

Protocol
  = behavioral contract

match
  = variant dispatch

generator
  = iterator

decorator/HOF
  = execution-policy composition

context manager
  = lifecycle protocol

module
  = namespace/facade/singleton-like instance
```

# 9. Algorithm versus pattern

```text
Algorithm:
  finite procedure for producing a result

Pattern:
  structural solution for assigning responsibilities
  under recurring design forces
```

Example:

```text
Algorithm:
  parse JSON characters into a syntax tree

Patterns around that algorithm:
  Factory
    select JSON parser

  Strategy
    inject parsing implementation

  Adapter
    normalize third-party parser API

  Decorator
    trace parsing duration

  Pipeline
    parse → normalize → validate

  State machine
    received → parsed → validated
```

The algorithm performs the work.

The pattern determines:

```text
where it lives
how it is selected
how it is composed
who invokes it
how it is replaced
how failures propagate
```

# 11. Practical classification rule

For each requirement, classify the sentence:

```text
"The system contains..."
  ─► Data

"The value must..."
  ─► Invariant

"The system calculates..."
  ─► Algorithm/operation

"The implementation depends on..."
  ─► Factory/strategy

"Before and after every operation..."
  ─► HOF/decorator

"The system calls A, then B..."
  ─► Pipeline/orchestrator

"When state X receives event Y..."
  ─► State machine

"The same operation must support backend Z..."
  ─► Port/adapter

"The system repeatedly drives X toward Y..."
  ─► Reconciler
```

# 12. Compressed ontology

```text
Domain
  = Data + Rules + Operations

Pattern
  = arrangement of Operations around Variability and Control

Factory
  = Config → Capability

Strategy
  = selected Algorithm

HOF
  = Operation → Operation

Adapter
  = Abstract Operation → Concrete Effect

Orchestrator
  = State × Operations → State

Dataclass
  = Data representation

Algorithm
  = Operation implementation
```

Therefore:

```text
dataclasses + algorithms
  ≠ design patterns

dataclasses + algorithms
  + explicit variability
  + composition
  + control ownership
  + effect boundaries
  = data-oriented realization of design patterns
```
