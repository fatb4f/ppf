# Result

The strongest fit is not an ontology of design patterns.

It is a:

```text
typed strategic operator IR
```

or:

```text
executable operator grammar
```

The closest synthesis is:

```text
algoctrl
  :=
    typed operator metamodel
  + strategy-combinator algebra
  + typed state DAG
  + implementation/runner boundary
  + observations and dispositions
```

Your existing `algoctrl_tmpl` already contains the macro-control skeleton:

```text
GEN → STRUCT → SELECT → FLOW → EVAL
```

with observable state, bounded feedback and explicit termination.

# High-signal ecosystem bubbles

## 1. Strategic rewriting: **Stratego / Spoofax**

### Kernel

```text
Rewrite rule
    = local transformation

Strategy
    = controls where, when and how rules apply
```

```text
rule:
    State → State

strategy:
    Rule → CompositeRule
```

Stratego provides primitive strategy combinators including:

```text
id
fail
sequence
left-choice
guarded-choice
nondeterministic-choice
recursion
all
one
some
top-down traversal
bottom-up traversal
fixed-point normalization
```

The key design decision is the separation of **small transformation rules** from **strategies controlling their application**. This is extremely close to the distinction you were establishing between lower-level algorithms, HOF-like strategies and orchestration. ([Spoofax][1])

### Mapping

```text
algoctrl operation
    ≈ Stratego rewrite rule

algoctrl strategy
    ≈ Stratego strategy expression

algoctrl feedback loop
    ≈ repeat / recursion / innermost

algoctrl normalization
    ≈ fixed-point strategic rewrite
```

### Fit

```text
primitive algorithm catalog:    very high
strategy composition:           very high
typed dataflow DAG:              medium
effect modelling:                low
Python ergonomics:               medium-low
```

**Primary concept to steal:** strategies must be separate from transformations.

## 2. Extensible semantic IR: **MLIR**

### Kernel

MLIR models computation using:

```text
Dialect
  ├── Operation
  ├── Type
  ├── Attribute
  ├── Property
  ├── Trait
  └── Interface
```

An operation definition can declare:

```text
operands
results
attributes
properties
regions
successors
constraints
traits
interfaces
builders
verification
```

Its operation-definition system generates implementation code from declarative records. Its rewrite system represents transformations as DAG-to-DAG patterns with match constraints, replacement graphs, benefits and application drivers. ([MLIR][2])

### Mapping

```text
algoctrl OperatorDef
    ≈ MLIR operation definition

operator family/domain
    ≈ dialect

semantic property
    ≈ trait

shared behavioral capability
    ≈ interface

input/output contract
    ≈ operands/results/types

invariant
    ≈ verifier/constraint

optimization or normalization
    ≈ rewrite pattern

pattern execution policy
    ≈ rewrite driver
```

### Fit

```text
operator metamodel:              extremely high
typed graph representation:      extremely high
traits and capabilities:         extremely high
strategy algebra:                medium
stateful workflow semantics:     medium
implementation weight:           very high
```

**Primary concept to steal:** an operation is not just a function name. It has a declarative signature, traits, effects, constraints and verification rules.

## 3. Portable operator algebra: **Substrait**

### Kernel

Substrait explicitly aims to define a cross-language specification for **what should be done to data**. It specifies types, functions, relational operations, extensions and serialized execution plans. Plans are trees or DAG-like compositions of operations, with extension points for new types and functions. ([Substrait][3])

```text
Plan
  └── Relation
        ├── input relations
        ├── expressions
        ├── functions
        ├── output schema
        └── properties
```

### Mapping

```text
algoctrl catalog
    ≈ portable operation specification

operator implementation
    ≠ operation semantics

logical operation
    → backend-specific physical implementation

extension catalog
    → registered domain operations

serialized plan
    → portable algorithm DAG
```

### Fit

```text
portable operation catalog:      extremely high
formal type signatures:          high
extension mechanism:             high
runner independence:             high
general algorithm coverage:      medium
non-data state transitions:      low
```

**Primary concept to steal:** specify the logical operation independently of the system executing it.

---

## 4. Dataflow graph and runner split: **Apache Beam**

### Kernel

```text
PCollection
    = immutable typed data state

PTransform
    = operation over PCollections

Pipeline
    = DAG of transforms and values

Runner
    = implementation of graph execution
```

Beam treats a transform as an input-to-output operation, allows transforms to be composite, and separates pipeline construction from execution by a selected runner. ([Apache Beam][4])

### Mapping

```text
StateType
    ≈ PCollection type

Operator
    ≈ PTransform

Strategy
    ≈ composite transform

Plan
    ≈ Pipeline DAG

Adapter/orchestrator
    ≈ Runner
```

### Fit

```text
typed state DAG:                 extremely high
operation composition:           high
implementation separation:       high
control branching:               medium
state machines/reconciliation:   low
```

**Primary concept to steal:** operations and intermediate states should both be first-class graph nodes.

---

## 5. Executable semantics: **K Framework / Maude**

### Kernel

K represents complete system state as structured **configurations**, then defines transitions through rewrite rules. K specifications are executable and can support state exploration and verification. ([K Framework][5])

```text
Configuration
    = complete observable state

RewriteRule
    = guarded state transition

Execution
    = repeated rule application
```

Maude adds an explicit strategy language for controlling potentially nondeterministic rewrite rules while preserving separation between local transformations and global execution strategy. ([arXiv][6])

### Mapping

```text
State
    ≈ configuration

Operation
    ≈ rewrite rule

Precondition
    ≈ rule match/guard

Postcondition
    ≈ resulting configuration

Strategy
    ≈ controlled rule application

Conformance
    ≈ reachability/invariant property
```

### Fit

```text
transition semantics:            extremely high
formal verification:             extremely high
algorithm catalog usability:     medium
routine Python implementation:   low
```

**Primary concept to steal:** define each operation as a legal transition over explicit state, not merely as executable code.

---

## 6. Bounded transformation cycles: **OpenRewrite**

### Kernel

OpenRewrite recipes are composable search/transformation operations over semantic trees. Its lifecycle includes configuration validation, parsing, preconditions, scanning, generation, editing, repeated cycles and explicit results containing before/after state and provenance. ([OpenRewrite Docs][7])

```text
parse
  → validate recipe
  → test preconditions
  → scan
  → generate
  → edit
  → compare result
  → repeat if required
```

Recipes are expected to be deterministic, idempotent and immutable; additional cycles are explicitly declared. ([OpenRewrite Docs][8])

### Mapping

```text
acquire/parse
    → semantic state

scan
    → observations/accumulator

precondition
    → admission guard

generate
    → candidate artifacts

edit
    → state transformation

result
    → evidence

causesAnotherCycle
    → bounded feedback declaration
```

### Fit

```text
practical lifecycle model:       extremely high
evidence/provenance:             high
bounded feedback:                high
general operator ontology:       medium
```

**Primary concept to steal:** feedback cycles should be declared by the operation, not inferred from arbitrary orchestration code.

## 7. Candidate-space reasoning: **egglog / equality saturation**

### Kernel

```text
facts + rewrite rules
  → saturation/fixpoint
  → equivalent candidate space
  → cost-based extraction
  → selected representation
```

Egglog combines Datalog-style facts with equality saturation, allowing incremental reasoning, rewrite-driven candidate generation and optimized-term extraction. ([arXiv][9])

### Mapping

```text
GEN
    → produce alternatives

STRUCT
    → merge equivalent candidates

SELECT
    → extract according to cost model

EVAL
    → lattice analysis / cost
```

### Fit

```text
candidate generation:            extremely high
normalization:                    extremely high
selection:                        high
general effects/orchestration:    low
```

**Primary concept to steal:** a candidate set can be represented declaratively and selected using an explicit extraction policy.

# Direct arXiv hits

## A. **A Grammar of Machine Learning Workflows**

This 2026 preprint is almost a domain-specific instance of what you are describing.

It defines eight kernel primitives:

```text
split
cv
prepare
fit
predict
evaluate
explain
assess
```

These primitives have typed input/output signatures and form a typed DAG. Higher-level strategy families—selection, optimization, evaluation and ensemble construction—reduce to compositions of the kernel primitives. The paper explicitly distinguishes kernel primitives from strategies. ([arXiv][10])

```text
primitive:
    fit : PreparedData → Model

strategy:
    screen :=
        foreach algorithm:
            fit → evaluate
        rank → select
```

This is an especially strong precedent for:

```text
small typed verb catalog
+ hard composition constraints
+ higher-level strategy catalog
+ terminal output types
```

---

## B. **The Maude Strategy Language**

This work directly formalizes:

```text
local rewrite rules
    ≠
strategies controlling rule application
```

Strategies handle nondeterminism, goal-directed execution and efficiency while preserving rule reuse. ([arXiv][6])

This is the strongest formal precedent for your:

```text
algorithm
    vs
algorithm-control strategy
```

distinction.

## C. **CADENZA**

CADENZA compiles semantic operator instances into typed task DAGs, applies dependency-checked structural rewrites, enumerates alternative plans and selects an executable plan under quality, latency and cost constraints. ([arXiv][11])

Its control model is:

```text
intent
  → operator template
  → typed task DAG
  → safe structural rewrites
  → candidate plan space
  → multi-objective selection
  → physical implementation/router
```

That closely matches:

```text
GEN → STRUCT → SELECT → FLOW → EVAL
```

---

## D. **Schema-gated orchestration**

A recent workflow paper proposes validating the complete composed workflow—including cross-step dependencies—against a machine-checkable schema before anything executes. ([arXiv][12])

This supplies the missing whole-DAG gate:

```text
Operator validation
    is insufficient

Plan validation
    must include:
        nodes
        edges
        dependencies
        capabilities
        constraints
        terminal conditions
```

# Relationship to factories and HOFs

```text
OperatorDefinition
    describes:
        what transformation means

Algorithm implementation
    performs:
        the transformation

Factory/provider
    resolves:
        OperatorDefinition × Environment
            → concrete implementation

HOF/strategy
    transforms:
        Operator → Operator

Plan
    composes:
        operators into a graph

Orchestrator/runner
    interprets:
        Plan × Bindings → Execution

Evaluator
    maps:
        Observation → Disposition
```

Compressed:

```text
factory
    selects an implementation

algorithm
    changes state

strategy/HOF
    controls algorithm application

DAG
    declares composition

runner
    executes the composition

ontology
    defines the vocabulary

metamodel
    defines valid operator descriptions

contract
    rejects invalid operators and plans
```

# Recommended identity

```text
algoctrl:
    a typed strategic operator grammar
    for constructing, validating and executing
    bounded algorithmic control DAGs
```

The closest practical architecture is:

```text
MLIR ODS
    for operator definitions, traits and verification

Stratego/Maude
    for the strategy-combinator algebra

Beam/Substrait
    for typed DAGs and runner independence

OpenRewrite
    for preconditions, bounded cycles and evidence

K
    for optional formal transition semantics

egglog
    for candidate generation and extraction
```

That combination is substantially closer to the intended concept than GoF design patterns or a conventional workflow engine.
