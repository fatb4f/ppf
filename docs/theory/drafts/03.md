## Yes—there are several close precedents

What does **not** exist as a dominant, commonly taught standard is one minimal notation that unifies:

```text
type signatures
+ pattern roles
+ structural relations
+ invariants
+ state transitions
+ failure semantics
+ implementation selection
+ algorithmic control
```

Those concerns are distributed across separate academic and professional traditions.

# Nearest established models

| Your representation element             | Established tradition                                     | Typical form                                        |
| --------------------------------------- | --------------------------------------------------------- | --------------------------------------------------- |
| `Config → Capability`                   | **Algebraic specification / typed functional signatures** | sorts, operations, signatures, axioms               |
| concepts and relations                  | **Ontology / conceptual modelling**                       | classes, properties, relations, restrictions        |
| valid model structure                   | **Metamodelling: MOF/UML**                                | metaclasses, associations, cardinality, constraints |
| inputs, outputs, preconditions          | **Hoare logic / Design by Contract / OCL**                | `{P} operation {Q}`                                 |
| states and guarded transitions          | **Operational semantics / state machines**                | `State × Event → State`                             |
| sequencing, branching, synchronization  | **Petri nets / workflow patterns**                        | places, transitions, tokens, control-flow patterns  |
| pattern participants and collaborations | **GoF/POSA pattern descriptions**                         | intent, context, participants, collaborations       |
| formal pattern conformance              | **Design-description languages such as LePUS3**           | classes, methods and relations constrained by logic |
| components, ports and connectors        | **Architecture description languages**                    | components, interfaces, connectors, configurations  |
| reusable computational structures       | **Algorithmic skeletons**                                 | map, reduce, pipeline, farm, divide-and-conquer     |

CASL is particularly close to your function-like expressions: it defines signatures containing data sorts and operations, then adds axioms and modular architectural specifications. ([Springer][1])

MOF provides the machinery for defining metamodels, while OCL adds executable constraints over models, including invariants and operation conditions. ([OMG][2])

Workflow-pattern research performs a similar operation for control flow: it catalogs recurring constructs such as sequence, parallel split, synchronization, choice, cancellation and termination, and gives them formal Petri-net semantics. ([Workflow Patterns][3])

LePUS3 is an especially direct precedent for formalizing object-oriented design patterns: it is explicitly described as a formal design-description language for capturing OO design building blocks. ([Essex Open Access Research Repository][4])

# Where your notation belongs

Your expression:

```text
Factory :=
    discriminator/configuration
      → implementation/capability
```

is simultaneously three things.

```text
TYPE SIGNATURE
    Factory : Configuration → Capability

ALGEBRAIC OPERATION
    factory(configuration) = capability

PATTERN SEMANTICS
    configuration selects a conforming implementation
```

A fuller formalization would be:

```text
sorts:
    Configuration
    Implementation
    Capability
    Failure

operations:
    select:
        Configuration → Implementation | Failure

    expose:
        Implementation → Capability

axioms:
    selected(i, c) ⇒ compatible(i, c)
    expose(i) satisfies required_capability(c)
    unknown(c) ⇒ select(c) = Failure.UnknownDiscriminator
```

That is recognizably **algebraic specification**.

Add participants and relations:

```text
Factory ─consumes──► Configuration
Factory ─selects───► Implementation
Implementation ─implements──► Capability
```

Now it is also a **metamodel or ontology fragment**.

Add guards and state changes:

```text
unresolved
  ──[configuration valid]──► selected
  ──[unknown discriminator]► rejected

selected
  ──[construction succeeds]► available
  ──[construction fails]───► failed
```

Now it also has **operational semantics**.

# Why there is no single standard presentation

Each tradition owns a different question:

```text
Algebraic specification
    What operations exist, and what laws must they satisfy?

Metamodelling
    What concepts and relationships may a model contain?

Ontology
    What do domain concepts mean and how are they related?

Design by Contract
    What must hold before and after an operation?

Operational semantics
    How does execution change state?

Workflow modelling
    How are operations ordered, branched and synchronized?

Design patterns
    How are responsibilities arranged under recurring design forces?

Algorithm analysis
    How is a computational problem solved efficiently?
```

They overlap, but their validation targets differ:

```text
CASL / algebraic specs
    theorem satisfaction

MOF + OCL
    model conformance

state machines
    legal transition behavior

Petri nets
    reachability, liveness, deadlock

GoF patterns
    architectural comprehension and reuse

algorithm catalogs
    correctness and complexity
```

Collapsing them into one model usually produces either:

```text
a formal language too heavy for routine programming
```

or:

```text
an informal notation too weak for proof and conformance
```

```text
    name:
        Factory

        selector

        selector consumes Configuration
        selector selects Implementation
        Implementation implements Capability

    operations:
        validate_configuration
        select_implementation
        construct_implementation
        expose_capability

        returned implementation satisfies Capability

        unresolved → validated
        validated → selected
        selected → constructed
        constructed → available

    failures:
        invalid_configuration

        unavailable_implementation

```

# Relationship to `algoctrl`

The repository still exists as `fatb4f/algoctrl_tmpl`. Its surviving canonical pipeline is:

```text
GEN → STRUCT → SELECT → FLOW → EVAL
```

with the semantics:

```text
GEN
    generate candidate state

STRUCT
    organize state and enforce invariants

SELECT
    prune the state space

FLOW
    control progression over time

EVAL
    decide, score or terminate
```

It also declares observable state, bounded feedback and explicit termination as core rules.

That is not primarily a GoF-style structural pattern catalog. It is closer to an:

```text
algorithmic control ontology
```

or:

```text
algorithmic skeleton metamodel
```

Its underlying universal loop is:

```text
state
  ▼
generate candidate
  ▼
structure / normalize
  ▼
constrain / select
  ▼
advance control
  ▼
evaluate
  ├─► terminate
  ├─► accept
  ├─► reject
  └─► feedback into generation
```

Your remembered vocabulary:

```text
acquire
normalize
validate
candidate
```

likely belongs to an ingress-oriented specialization of that more general ramp:

```text
ACQUIRE
  source → raw state

NORMALIZE
  raw state → canonical state

VALIDATE
  canonical state → admitted or rejected state

GENERATE
  admitted state → candidates

SELECT
  candidates → selected candidate

EXECUTE / FLOW
  selected candidate → observed result

EVALUATE
  observed result → disposition

REVISE
  disposition → updated state or termination
```

So the ingredients are well established. The distinctive part is combining them into one compact, executable vocabulary:

```text
Pattern
    = structural responsibility arrangement

Operator
    = typed state transformation

Control
    = composition of operators over time

Contract
    = constraints on data and transitions
```

That unified representation is not the standard curriculum, but it is a defensible synthesis of algebraic specification, metamodeling, operational semantics, workflow patterns and software pattern languages.
