# Integrated ontology stack

Do not merge every concept into one flat ontology. Use a layered stack with explicit conformance and specialization relations.

```text
L0  META-ONTOLOGY
      defines how concepts are described

L1  CORE ONTOLOGY
      defines universal engineering concepts

L2  DOMAIN ONTOLOGIES
      define PPF-specific concepts and relations

L3  OPERATOR / PATTERN ONTOLOGIES
      define computational and architectural behavior

L4  SCHEMA BINDINGS
      bind Pydantic types and fields to ontology concepts

L5  INSTANCE GRAPH
      contains actual policies, evaluations, diagnostics, evidence

L6  VIEW PROJECTIONS
      render selected perspectives in marimo/Bloom-like UI
```

# L3 — Operator and pattern ontologies

These are separate from the PPF domain ontology because they describe **how computation is performed**, not what PPF entities mean.

## Operator ontology

```text
Acquire
Decode
Parse
Normalize
Discriminate
Validate
Admit
Generate
Structure
Filter
Rank
Select
Execute
Observe
Evaluate
Decide
Repair
Publish
Terminate
```

Each is an `OperationType`.

```text
Discriminate:
    input:
        CandidateDocument

    output:
        DocumentKind | UnknownKind

    intent:
        Determine the semantic class governing further processing.

    precondition:
        Candidate document exposes the required discrimination surface.

    failures:
        missing discriminator
        ambiguous discriminator
        unknown discriminator
```

## Control ontology

```text
Sequence
Branch
Guard
Repeat
Retry
Fallback
Parallel
Race
Fixpoint
Reconcile
Compensate
Terminate
```

These are higher-order operations:

```text
Sequence:
    Operation × Operation → Operation

Retry:
    Operation × RetryPolicy → Operation

Guard:
    Predicate × Operation → Operation
```

## Pattern ontology

```text
Factory
Strategy
Adapter
Pipeline
StateMachine
Repository
Builder
Supervisor
Reconciler
```

A pattern references operators and roles.

```text
Factory:
    roles:
        discriminator
        selector
        implementation
        capability

    operations:
        validate
        discriminate
        select
        construct
        expose

    invariant:
        selected implementation provides required capability
```

This creates the precise relationship:

```text
Factory ──uses_operation────► Discriminate
Factory ──uses_operation────► Select
Factory ──uses_operation────► Construct
```

A concrete Python factory then realizes both layers:

```text
make_parser()
    ├── implements────► Factory
    ├── implements────► Discriminate
    ├── implements────► Select
    └── returns────────► ParsingCapability
```

# Integration through Pydantic annotations

Pydantic types bind implementation schemas to ontology concepts.

## Model binding

```python
from pydantic import BaseModel, ConfigDict


class Policy(BaseModel):
    model_config = ConfigDict(
        json_schema_extra={
            "x-semantic-node": {
                "concept": "ppf.policy:Policy",
                "identity_field": "policy_id",
                "label_field": "title",
                "description_field": "description",
            }
        }
    )

    policy_id: str
    title: str
    description: str
```

This means:

```text
Python type Policy
    ──realizes──► ppf.policy:Policy
```

## Relationship binding

```python
from typing import Annotated
from pydantic import Field


EvaluationRefs = Annotated[
    list[str],
    Field(
        json_schema_extra={
            "x-semantic-edge": {
                "relation": "ppf.evaluation:evaluated_by",
                "target_concept": "ppf.evaluation:EvaluationCase",
            }
        }
    ),
]
```

```python
class Policy(BaseModel):
    policy_id: str
    title: str
    description: str
    evaluation_ids: EvaluationRefs = []
```

This binds:

```text
Policy.evaluation_ids
    ──realizes──► evaluated_by
```

## Operation binding

Functions can use typed decorators or metadata.

```python
@semantic_operation(
    concept="algoctrl:Discriminate",
    inputs=["ppf.contract:CandidateDocument"],
    outputs=["ppf.contract:DocumentKind"],
)
def discriminate_document(document: dict[str, object]) -> str:
    ...
```

This adds an implementation relation:

```text
discriminate_document
    ──implements──► algoctrl:Discriminate
```

# Compiled semantic catalog

The annotations should not be interpreted independently at every graph build.

Compile them first.

```text
Pydantic model catalog
    +
core ontology
    +
domain ontologies
    +
operator ontology
    +
pattern ontology
        │
        ▼
CompiledSemanticCatalog
```

```text
CompiledSemanticCatalog:
    concepts
    relations
    operations
    patterns
    model_bindings
    field_bindings
    function_bindings
    description_templates
    validation_rules
```

The compiler validates:

```text
referenced concepts exist
relation source type is valid
relation target type is valid
inverse predicates agree
cardinality is coherent
operation signatures compose
descriptions have required variables
concept specialization is acyclic
```

# Runtime integration DAG

```text
S0: LOAD META-ONTOLOGY
    output:
        valid ontology-definition vocabulary
```

```text
S1: LOAD ONTOLOGIES
    inputs:
        core
        PPF domains
        operator catalog
        pattern catalog

    output:
        unified concept registry
```

```text
S2: ALIGN ONTOLOGIES
    actions:
        resolve shared concepts
        register specialization
        register equivalence
        reject conflicting meanings

    examples:
        PolicyFinding specializes CoreFinding
        EvaluationEvidence specializes CoreEvidence
        Factory discriminate uses OperatorDiscriminate
```

```text
S3: INTROSPECT PYDANTIC
    actions:
        read model annotations
        read field annotations
        read operation annotations

    output:
        schema-to-ontology bindings
```

```text
S4: COMPILE CATALOG
    actions:
        validate bindings
        materialize node and edge type definitions
        compile description templates

    output:
        CompiledSemanticCatalog
```

```text
S5: ACQUIRE INSTANCE CORPUS
    input:
        PPF JSONL documents
```

```text
S6: DISCRIMINATE
    action:
        document discriminator
            → bound Pydantic model
            → ontology concept
```

```text
S7: VALIDATE
    action:
        structural validation
        domain invariant validation
        ontology-binding validation
```

```text
S8: MATERIALIZE
    output:
        instance nodes
        typed edges
        provenance records
```

```text
S9: ENRICH
    actions:
        attach operation implementations
        attach pattern realizations
        derive inverse edges
        generate deterministic descriptions
```

```text
S10: PROJECT
    input:
        perspective definition

    output:
        bounded view graph
        relationship narrative
```

# Description-resolution hierarchy

Descriptions can come from several ontology levels.

```text
1. Instance rationale
2. Field-binding template
3. Domain relation template
4. Core relation template
5. Generic fallback
```

Example:

```text
Domain relation:
    Evaluation ──evaluates──► Policy

template:
    "{source.label} evaluates whether {target.label} is satisfied."
```

Field-specific override:

```text
Policy.evaluation_ids:

    "{source.label} is qualified by {target.label} using admitted observations."
```

Instance rationale:

```text
HO-01 evaluates Baseline Required because repair must be compared
against an admitted pre-repair observation.
```

Rendered output uses the most specific available description.

# Critical separation

```text
Ontology:
    defines what Policy, Evaluation and Diagnostic mean

Metamodel:
    defines how ontology concepts and relations are represented

Pydantic binding:
    declares which Python type realizes each concept

JSONL corpus:
    supplies concrete instances

Operator ontology:
    defines transformations such as discriminate and validate

Pattern ontology:
    defines recurring arrangements of operators and roles

Perspective:
    chooses which portion of the complete graph to display
```

# Resulting unified graph

```text
                         META LAYER
            EntityType, RelationType, OperationType
                              │
                         instantiates
                              ▼
                       ONTOLOGY LAYER
       Policy, Evaluation, Diagnostic, Validate, Factory
                              │
                          realized_by
                              ▼
                        MODEL LAYER
        Pydantic classes, fields, functions, workflows
                              │
                         instantiated_by
                              ▼
                       INSTANCE LAYER
       policy:P-01, evaluation:HO-01, diagnostic:D-04
                              │
                         projected_as
                              ▼
                         VIEW LAYER
             marimo graph + relationship narrative
```

The practical integration unit is therefore:

```text
SemanticCatalog
    =
        MetaOntology
      + CoreOntology
      + DomainOntologies
      + OperatorOntology
      + PatternOntology
      + PydanticBindings
```

The graph is then:

```text
DescribedSemanticGraph
    =
        SemanticCatalog
      × ValidatedPPFCorpus
      × Perspective
```

This lets a single selected PPF policy be explored simultaneously as:

```text
a domain rule
a schema-bound type instance
an evaluation target
a diagnostic source
an implementation responsibility
a participant in an algorithmic workflow
and a realization of architectural patterns
```
